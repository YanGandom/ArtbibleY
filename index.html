01. 项目概况与配置

1.1 项目定位

  • 项目类型：欧美卡通 3D 休闲游戏，覆盖 Merge、装修、剧情与活动内容等常见玩法。
  • 运行环境：Unity；目标平台与设备档位由项目立项文件确认。
  • 团队模式：中小型团队，专业模块分工，部分模块可并行制作或通过外包扩容。
  • 工作目标：建立从概念设计到 美术制作软件 制作、Unity 集成、验收发布的可重复生产流程。

1.2 生产原则

原则执行定义
风格先行通过美术圣经、关键视觉样板和统一参考库定义比例、轮廓、色彩、材质、灯光与细节密度。
模块化生产优先识别可复用资产、组件、家具部件、角色换装和 UI 组件，避免重复制作。
引擎结果为准美术制作软件 视口和设计工具中的效果只是制作参考；最终结果必须在 Unity 的目标相机、灯光和平台设置下验证。

02. ArtBible · 美术风格指南

本章用于统一 Project Y 的视觉方向，作为角色、场景、UI、动画与特效制作的风格参考。以下为初步占位内容，后续补充参考图、色板、样板资产和具体规范，并经主美评审确认。

2.1 视觉定位与关键词

沿用当前项目定位，以欧美卡通 3D 休闲风格为基础。初步关键词：亲和、明快、轮廓清晰、层次易读。

待补充：目标受众、世界观、情绪基调、风格参考图及不采用的视觉方向。

2.2 色彩、材质与光照

初步方向：通过清晰的主次色和柔和的光照突出重点，保持材质表达简洁，确保小尺寸下的可读性。

待补充：主色与辅助色、色板数值、材质样板、灯光模板及 Unity 内效果截图。

2.3 角色与场景

初步方向：角色轮廓具有辨识度，场景与家具保持统一的比例和造型语言；Merge 物品在目标显示尺寸下能区分等级。

待补充：角色比例、表情规范、建筑与家具造型、物品链样板、正反例对照。

2.4 UI、动画与特效

初步方向：UI 信息层级清晰，动画反馈轻快，特效突出操作结果；三者的色彩与造型应与游戏世界保持协调。

待补充：字体与组件样式、图标风格、动效节奏、特效强度及代表性视频。

2.5 参考与样板库

  • 风格参考板：待补充链接与图片。
  • 已通过样板：待补充角色、场景、Merge 物品和 UI 的样板资产。
  • 风格禁区与反例：待补充不符合项目方向的示例及说明。
  • 评审与更新记录：待补充负责人、确认日期及修订说明。

3.2 管理与协作角色

  • 主美 / 美术负责人：对整体风格、视觉品质、资产优先级和跨模块评审负责。
  • 模块负责人：对本模块任务拆分、人员安排、首轮评审、风险与返修闭环负责。
  • 制作人员：对任务单范围内的源文件、资源完整性、自检结果和修改记录负责。
  • 客户端 / UI 实施：负责游戏逻辑、运行时 UI 组装、资源引用与程序实现；若项目另设 UI 实施岗位，需在立项时明确职责。
  • QA：负责按测试计划验证功能、设备适配和缺陷回归；美术 QA 可由模块负责人或专职人员承担。

3.3 重要职责边界

交界面责任约定
场景原画 ↔ 场景 3D原画负责设计意图与拆分说明；场景 3D 负责可生产的三维实现，并在结构不可行时提出反馈。
角色原画 ↔ 角色 3D角色原画负责设计与换装关系；角色 3D 负责模型实现、材质和绑定所需的技术准备。
角色原画 ↔ Spine 动画原画负责角色设计、分层绘制与补画；动画师负责拆件需求、骨骼、网格、权重与动画。双方提前确认动作范围与拆件方案，详见 5.3 角色原画及 5.7 2D 动画与 UI 动画。
角色 3D ↔ 3D 动画角色 3D 交付适合绑定和变形的模型；绑定/蒙皮由角色 3D 或动画岗位承担，项目必须明确唯一责任人。
UI/UX ↔ UI 动画UI/UX 定义界面结构、视觉稿和需要表现的状态；UI 动画师负责运动节奏、关键帧、状态过渡与动画资源。
UI 动画 ↔ UI 特效UI 动画负责元素本身的运动；特效负责粒子、发光、溶解、爆闪、轨迹等视觉特效。
各工种 ↔ TA各工种对资产内容与自检负责；TA 对通用工具、导入规则、技术诊断和自动化方案负责，不替代所有人的日常制作责任。
Merge 设计 ↔ 资产制作策划提供物品 ID、等级、功能和合成关系；指定美术主责完成整链视觉设计，模型与图标制作按任务单接收。待确认：整链设计归属及各链负责人。
3D 资产 ↔ 图标出图模型制作人交付可渲染资产；指定出图负责人按统一镜头、灯光和裁切模板生成图标，UI 设计确认目标尺寸下的显示效果。待确认：渲染出图、修图与最终导出岗位。
美术交付 ↔ Unity 集成制作人负责资源完整与自检；集成主责负责导入、引用和配置，客户端负责业务逻辑；视觉由美术复验。待确认：各类资源集成主责名单。
Shader / 材质 ↔ VFXTA 维护公共 Shader 与材质模板；VFX 负责具体效果与参数。新增通用功能由双方评估，明确维护人与版本。

每项交付物在任务单中指定一位主责、一位接收人和一位最终审核人；协作者可以多人。岗位归属尚未确认时，由美术负责人在开工前完成分配。

04. 生产流程与验收

4.1 项目里程碑

阶段执行内容主要输出 / 检查点
M0 项目定义明确玩法、平台、内容范围、竞品方向、品质目标与资源规模。美术需求总表、模块边界、初步资源清单和风险清单。
M1 风格预研探索角色、场景、道具、UI、动画、特效的视觉方向。美术圣经 V1、关键视觉、风格参考库、主美评审记录。
M2 技术预研验证模型、材质、灯光、UI、动画、特效与 Unity 的实际表现。技术验证报告、导入预设草案、性能采样、工具链决策。
M3 垂直切片选取典型角色、装修场景、物品链、UI 和动态效果走通全流程。可运行样板、实际工时、返修记录、首轮技术预算。
M4 规范固化根据切片结果制定各工种 SOP、命名、目录、模板和验收标准。工种规范 V1、交付模板、检查清单、责任矩阵。
M5 批量生产各专业并行生产，按模块和批次进行视觉、技术与进度管理。批次资产包、评审记录、资源状态看板、工时统计。
M6 集成与优化Unity 集成、状态组合、设备适配、性能优化和缺陷回归。可运行版本、性能报告、缺陷清单、资源依赖检查。
M7 发布与维护版本冻结、资源归档、上线检查、后续内容更新和流程复盘。发布资产包、可追溯源文件、更新规范、复盘记录。
里程碑通过条件未通过时的处理
风格锁定角色、场景、道具、UI、动画和特效至少有代表性样板，风格规则可被不同人员复现。补充样板与禁用案例，明确需要修订的风格规则。
技术预研通过导入、材质、动画、UI 适配和性能风险已在目标环境中验证。缩小范围做专项实验，不将未验证方案扩散到批量生产。
垂直切片通过从设计到 Unity 运行时的完整链路跑通，工时与返修有记录。调整资源预算、职责边界、工具选型或验收条款。
批次验收通过批次资产满足视觉、技术、引擎和性能要求，缺陷已关闭或获得明确例外批准。退回具体环节修复，避免将问题带入下游批次。

4.2 资产状态与评审

状态进入 / 退出条件主责动作
待制作需求、输入、交付物、接收人、审核人及排期明确。任务主责确认前置依赖。
制作中按工种流程制作，在关键节点提交方案或样板。制作人自检，提前提出风险。
待评审提交完整版本及自检记录，按适用质量门检查。审核人给出通过或具体返修意见；记录各质量门结果。
返修中记录问题、责任人、修复范围与目标日期。修复后回到受影响的质量门，不重复无关检查。
已通过适用质量门通过，阻断问题关闭；延期项符合缺陷规则。审核人确认是设计交付通过还是运行时资产通过。
已归档批准文件、依赖、预览、记录与版本可追溯。任务主责归档，接收人确认可使用。

4.3 质量门与适用范围

质量门检查内容适用范围
G1 视觉验收依据 ArtBible 检查风格、轮廓、比例、色彩与可读性。所有视觉交付物；设计稿在约定尺寸或视角下检查。
G2 交付技术验收源文件、分层、命名、尺寸、格式、依赖及下游可用性。所有交付物；只检查与资产类型相关的技术项。
G3 Unity 验证目标场景中检查显示、引用、适配、状态切换及实际行为。进入引擎的运行时资源；原画和纯设计稿不单独要求通过此门。
G4 性能验收依据批准预算，在目标设备与代表性场景测量。有运行时成本的资源或批次；通过后统一归档。

设计交付通过表示可以进入下游制作，不代表运行时成品通过。各质量门的审核人写入任务单；不适用项标注 N/A 并说明原因。

4.4 缺陷与放行规则

级别定义交付规则
P0 阻断崩溃、无法加载、核心内容不可用或重大版本风险。阻断交付与发布，修复并复验后关闭。
P1 严重核心视觉、关键交互、主流程资源或性能存在严重问题。默认阻断交付与发布；特殊放行须记录风险、批准人、修复期限和回归范围。例外审批名单待确认。
P2 一般局部瑕疵、轻微不一致或非关键适配问题。可由指定审核人批准延期，记录负责人、修复版本与时间；未批准的延期项仍须处理。
P3 优化不影响使用的精修或增强建议。进入优化列表，不阻断交付；保留责任人与处理决定。

验收不要求所有优化建议关闭：P0 必须关闭，P1 按阻断或正式例外处理，P2 按批准计划处理，P3 纳入优化列表。缺陷单模板见附录。

4.5 通用交付与归档清单

  • □ 任务 ID、需求版本、主责、接收人和审核版本对应。
  • □ 源文件可打开，依赖完整，导出格式、命名与目录符合项目规则。
  • □ 适用质量门与本工种专项检查通过，不适用项有说明。
  • □ 问题按 4.4 处理，修复与延期决定可追溯。
  • □ 源文件、正式输出、预览、自检与验收记录已归档。

05. 各工种制作规范

各工种采用“输入确认 → 关键制作步骤 → 下游交付 → 专项检查”。以下保留专业特有要求，命名、归档与通用验收统一执行 4.5；软件与版本统一查阅 7.1 和项目配置。

5.1 场景原画

负责空间概念、场景氛围、装修方案、家具风格、构图与资产拆分。

阶段执行内容主要输出 / 检查点
需求拆解确认场景用途、镜头、装修阶段、空间限制、玩家可见区域和资产复用要求。场景需求单、参考需求清单。
参考与风格板收集轮廓、材质、配色、空间层次与氛围参考，标注可采用内容。风格板、参考来源与采用说明。
构图与方向探索先比较空间布局、视觉重心和色彩关系，再细化局部设计。多个方向草案、评审截图。
方案评审确认结构、视角、装修前后差异、资源量和重点资产。通过的方案与评审记录。
正式细化完善关键结构、家具、配件、材质分区和主色辅助色。正式概念图、关键细节图、色板。
生产拆分给出固定结构、可替换部件、单体家具、装饰件与阶段变化。资产拆分图、视图、尺寸 / 轴心说明。
下游交接与场景 3D 检查可生产性，并根据反馈修订。交接清单、禁改项和最终批准版本。

交付与验收

  • □ 目标相机下的空间构图、层次与重点明确。
  • □ 装修前后状态差异清楚，固定结构与可替换资源拆分合理。
  • □ 主要部件有足够的结构、色彩和材质说明。
  • □ 关键资产的正面 / 侧面 / 背面或安装视图满足建模需要。

5.2 场景 3D

阶段执行内容主要输出 / 检查点
确认设计与模块规则确认比例、单位、安装面、轴心、网格、材质类型和复用范围。资产规格、轴心与命名约定。

交付与验收

  • □ 模型比例和轮廓符合设计，拼接处无明显缝隙或交叠。
  • □ 轴心、单位、朝向、法线、UV 和材质分配正确。
  • □ 贴图尺寸、格式与导入设置符合对应资产等级。
  • □ Prefab 层级、组件、引用和材质依赖完整。
  • □ 在目标镜头和灯光下确认颜色、轮廓、遮挡与视觉重点。
  • □ 面数、材质数、贴图内存等预算在切片制定的范围内。

5.3 角色原画

负责角色外观、比例、服装、配件、表情与换装设计。设计确认后，按用途进入三维制作交接或 Spine 素材交接。

阶段执行内容主要输出 / 检查点
角色需求分析确认角色定位、性格、用途、镜头占比、动画需求和可换装范围。角色需求单、风格与参考方向。
轮廓与比例探索探索头身比、体块、姿态和服装轮廓。轮廓草图、比例对比。
服装与配件设计定义主要材质、装饰层级、颜色和可拆分部件。服装 / 配件方案。
评审与定稿确认角色辨识度、风格、生产成本和动画可行性。正式设定与评审记录。
生产视图整理按目标路径准备生产资料：三维制作补充必要视图；Spine 制作提供分层拆件、遮挡补画与替换件。按用途提交制作视图或分层 PSD、拆件与补画。
下游交接三维路径与角色 3D 确认结构、关节和换装；Spine 路径与动画师确认拆件、运动覆盖和代表性动作。交接文件、修改记录。

交付与验收

Spine 素材交接：用于 Spine 的角色，应先由原画与动画师共同确认动作清单、目标尺寸、拆件层级、遮挡关系及换装范围。原画按确认方案提供命名清晰的分层 PSD、完整部件与必要补画；动画师检查素材并用代表性动作验证可动性，再进入完整动画制作。若拆图由其他岗位执行，任务单须指定唯一负责人；补画与造型质量仍由角色原画负责。

  • □ 用于 Spine 的角色已完成拆件方案确认；关节覆盖、遮挡补画、表情替换件和素材版本满足动画需求。
  • □ 角色轮廓、比例与面部特征在目标视角下可识别。
  • □ 主色、辅助色、强调色和材质语言统一。
  • □ 服装与配件层级、遮挡关系和拆件范围清楚。
  • □ 用于三维制作的角色具备足够视图与关键部位说明；仅用于 Spine 的角色按实际动作视角交付。
  • □ 涉及动画或换装的部位已标注变形与兼容要求。

5.5 UI/UX 设计

阶段执行内容主要输出 / 检查点
需求与状态梳理梳理页面目的、用户路径、数据状态、异常状态和各类弹窗。UI 需求单、状态表、流程图。

UI 必须建立的规范

  • 基础组件：按钮、弹窗、页签、资源栏、倒计时、进度条、列表、滚动容器。
  • 状态规范：默认、悬停（如平台需要）、按下、禁用、选中、加载、成功、失败、解锁。
  • 布局规范：参考分辨率、安全区域、锚点策略、长宽比适配、字体与文本溢出规则。

交付与验收

  • □ 页面信息层级与视觉规范完整，关键状态无缺失。
  • □ 组件可复用且命名、变体和样式一致。
  • □ 文字、数字和多语言扩展空间已考虑。
  • □ 设计稿中标注了动画、特效和程序交互的需求位置。
  • □ 明确 UI 动画、UI 特效和 Unity 实施的责任人，UI 设计不承担其制作责任。

完整场景组合房间、庭院、店铺和剧情场景。统一相机、灯光、Prefab 层级及可交互对象命名。

  • 场景 ID、阶段 ID、固定资源列表、可替换槽位列表。
  • 每个阶段新增 / 删除 / 替换的资源与对应 ID。
  • 相机、灯光、遮挡与重点展示区域的要求。
  • 状态切换的动画与特效需求、程序触发依赖。
  • 同一房间跨阶段的复用率、新增资源数量和验收记录。

风格样板与反例统一查阅 ArtBible；镜头、灯光、预览场景与分级预算统一查阅项目配置。专项制作不另设相互冲突的基准。

7.1 工具与版本

下表说明工具用途，具体采用及版本以 1.3 的批准配置为准。

工作类型主 / 辅工具优势与适用场景边界与交付原则

7.2 源文件与工程管理

  • 美术源文件库与 Unity 运行时工程可以分开管理，但必须通过稳定的资源 ID 和交付流程关联。
  • 不要把所有高体积源文件无差别放入运行时目录；工程内保留实际需要的源文件或按团队策略管理。
  • 所有导入预设、材质模板、Shader、通用 Prefab 和检查规则由 TA 维护版本。
  • 禁止个人随意改变全项目导入设置、渲染设置或命名规则；变更应通过评审和版本记录。

7.5 资源变更控制

  • 修改公共材质、导入预设、Shader、UI 公共组件或命名规则前，必须评估影响范围。
  • 大规模资源重导入前应先在分支或测试场景验证，并保留回滚方式。
  • 正式交付时应记录使用的 Unity 版本、插件版本、渲染设置和资源批次。

已批准资源的需求、外观、动作范围或公共依赖发生变化时，记录影响资产、上下游接收人、工时与验收范围，批准后再更新。待确认：不同变更类型的审批人。

08. 协作与文档维护

8.1 任务与协作

每项任务使用附录的统一任务单，在开工前明确需求、依赖、交付与验收。可在同一任务系统建立不同视图，避免重复维护多套数据。

  • 资源生产看板：按工种、模块、资产 ID 和生产状态查看任务进度。
  • 评审 / 缺陷看板：跟踪评审意见、问题等级、责任人、复验与关闭状态。
  • 资源依赖看板：管理原画、模型、材质、绑定、动画、特效和引擎配置的前置关系。
  • 版本发布看板：追踪批次冻结、导入结果、性能基准、缺陷回归和归档状态。

8.2 评审与反馈

每条评审意见建议包含：问题位置、当前结果、目标结果、严重程度、建议修改方向、责任人、复验标准。意见应可执行、可复验；避免只有主观形容词而没有具体落点。

待制定：日常评审频率、提交截止时间、紧急问题响应方式与评审负责人名单。

8.3 效率与质量观察

指标用途注意事项
计划完成率 / 按期交付率观察排期、依赖与人力容量。需区分需求变更与制作延误。
首次评审通过率观察需求质量、样板有效性与制作规范清晰度。低通过率不应直接归因个人能力。
平均返修次数 / 返修工时占比识别风格不清、评审过晚或交付标准不一致。应按资产类型与难度分组。
单件实际工时用于下一批次资源估算和人力规划。区分制作、评审、集成和返修工时。
重复制作率 / 复用率识别目录、资产库和模块化设计的改善空间。复用要同时看维护成本与效果。
集成缺陷数量 / 引擎返工率衡量导入规范和前置技术验证效果。按问题类型追踪根因。
自动检查覆盖率 / 误报漏报率衡量工具能否真正降低人工检查负担。自动检查需要人工抽检与维护。

初期优先跟踪按期交付、首次评审通过、返修工时与集成缺陷，其他指标在有稳定记录后启用。待制定：统计周期、计算口径与数据维护人。

A.4 管线建设计划

阶段主要工作完成标志
第 1 阶段：基础搭建确认九大模块职责、目录命名、统一任务单、评审状态与通用质量门。团队能用统一流程创建、制作、提交和验收资源。
第 2 阶段：垂直切片挑选一个代表性房间、一条 Merge 物品链、一个角色、一组 UI、动画与 VFX。完整验证从设计到 Unity 的流程，并获得实际工时与性能数据。
第 3 阶段：工种规范固化补齐每个模块的 SOP、交付模板、技术预算、资源等级和验收清单。新人可以依照文档完成标准资产，负责人可以按清单验收。
第 4 阶段：工具化建立导入 Preset、自动检查、批量导出、依赖检查、统一预览模板。重复性问题可自动发现，常见工作流程可复用。
第 5 阶段：持续优化复盘工时、返修、集成缺陷、资源复用与自动化收益。规范按实际数据迭代，不因文档完成而停止维护。
